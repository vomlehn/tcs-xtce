Software tools for XTCE (XML Telemetric and Command Exchange): a compiler that turns a mission’s XTCE definitions of commands and telemetry into the data structures and code that pack and unpack them, in C/C++, Rust and Python; an XTCE editor; and tcsxtce, the operational runtime the generated code runs on, aboard and in the mission operations center. Made for space applications, and as useful on the ground, such as for drones.

Includes libraries that serialize and deserialize OMG XTCE (XML Telemetric and Command Exchange) data into managed, preallocated buffers, in two layers:

  • XML binding: typed data structures for the whole XTCE schema, with code that reads and writes XTCE documents. The code for all three languages is generated from the official schema, which is downloaded into references/.
  • Packet codecs: tcs-xtce compiles one mission’s XTCE document, or the several documents it is split across, as Yamcs loads them, into typed telemetry and command structs, with binary encoders and decoders for the packets it describes.

XTCE defines the data structures once, and the code generated for each language exchanges them: what one language writes, any other reads, byte for byte. The packets are bit-packed, so a field takes only the bits its encoding gives, with none of the padding a language’s own structures have; the housekeeping example’s status packet is 7 bytes, where the C structure is 40. Packets carry no field names or tags. Instead, programs check that they were built from the same definition by comparing digests, which every language (Rust, C/C++ and Python) computes the same way, as does xtce-digest: the sender sends its digest first, and the receiver checks it, which guarantees that they agree on every field’s type and order. That avoids the per-message cost of self-describing formats: the same packet is 77 bytes as JSON and 29 as Protocol Buffers.

What the generated code runs on, the packet runtime, and the digest programs check each other with are a library of their own, tcsxtce, in each language: the tcsxtce crate, the tcsxtce Python package, and the header-only tcsxtce-packet.h and tcsxtce-digest.h for C and C++. It is operational code, run aboard and in the operations center, and is all of tcs-xtce that is, with tcsccsds; the rest – the XML binding, the compiler and the editor – is software tools, which make what operational code is built from. categories.toml puts each directory in its category, as “Code categories” in tcs-helpers’ README defines them.

The full documentation is in docs/: docs/tcs-xtce.rst (the code generator’s manual, including every data structure and method), docs/tcs-xtcee.rst (the editor’s manual), docs/manual.rst (what each manual covers), and the design and rationale of each, docs/tcs-xtce-design.rst and docs/tcs-xtcee-design.rst, which docs/design.rst lists; each is rendered to HTML beside it: see See also.

Work is under way on integrating tcs-xtce with NASA’s core Flight System (cFS) and JPL’s F´ (F Prime): generating cFS messages and F´ FPP from XTCE, or reading their definitions into it, and dictionaries for their ground systems. The plan, shared with tcspecial and tcslog, is in tcspecial’s docs/third-party.rst.

Note: integration with cFS and F´ is a work in progress. None of it is built yet, and the plan may change as it is.

Building

make              # fetch references if missing, generate, build, run all tests
make rust         # build the Rust crates alone, from the generated binding
make cpp          # build the C++ library and its tools alone
make python       # byte-compile the Python packages alone
make references   # re-check OMG and pull the latest XTCE documents
make generate     # regenerate the bindings after the schema or generator changes
make samples      # regenerate the schema-coverage samples in tests/samples/
make packets      # regenerate the demo mission's packet codecs
make editor       # build tcs-xtcee, the XTCE editor, generating the Rust
                  # binding it is built on first
make test         # per-language tests, the seven cross-language checks
                  # (cross, packet, stream, digest, float, bnum, ccsds), the
                  # editor's tests, the examples, the page and name checks,
                  # and the 80-column check
make examples     # build and run the examples in examples/
make html         # remake the HTML pages from their reStructuredText
make screenshots  # remake the editor manual's screenshots
make fmt-check    # verify Rust and Python formatting (Rust is also checked by
                  # every `make rust`)
make python-dist  # build the Python wheels and sdists into dist/, and try them
make ccsds        # build tcsccsds, the CCSDS time codes: see ccsds/README.md

Plain make also checks the formatting and, in a git checkout, sets up the commit hook. The generated bindings are not committed, so a fresh clone runs make or make generate before anything is built from them; make editor and the language targets do it themselves.

Requirements:

  • git, make, pkg-config and binutils (strip, ar);
  • curl and xmllint;
  • Python 3.11+, with pip and venv (the Python packages themselves run on 3.10); setuptools 77 or later and twine for make python-dist and for installing and packaging, which build the Python in place, without pip’s isolated environment – where the system’s setuptools is older, python3 -m venv --system-site-packages ~/tcs-venv, ~/tcs-venv/bin/pip install 'setuptools>=77' twine, and PYTHON=~/tcs-venv/bin/python3 on each make line;
  • a Rust toolchain with rustfmt: the newest stable, which rust-toolchain.toml asks rustup for and make test holds it to, through tcs-helpers’ rust-current – run rustup update stable where it says a newer one is out. The editor needs 1.92 or later, which make install-tools checks;
  • a C11 and C++20 compiler, and fontconfig’s headers;
  • rst2html (python3-docutils) and pandoc for the pages make test checks;
  • a checkout of tcs-helpers, 0.11.0 or later, beside this one: make test’s page and name checks, installing and packaging all use it;
  • the network, the first time: crates.io for every cargo build, omg.org for the references and the schemas the editor’s tests use, and GitHub for the public documents make samples-check reads;
  • podman, only for make python-versions and make portable-packages, and gh, only for make publish-release.

make install-tools installs all but the checkout, podman and gh with apt-get or dnf, and says what it cannot install; DRY_RUN=1 shows the commands and runs none, and PACKAGING=0 leaves out the packaging tools. It is bin/install-tools, which a container can run as root too. tcs-xtce needs nothing of TCSpecial’s, and is used with it or on its own.

references/Makefile finds the latest version on the OMG specification page (https://www.omg.org/spec/XTCE/) rather than hard-coding it. At the time of writing that is XTCE 1.3, schema namespace http://www.omg.org/spec/XTCE/20250214.

Installing

Everything below installs under /opt/tcs, the tree the TCS packages share: the tcs-xtce, xtce-digest and tcs-xtcee commands in bin/, the C/C++ headers in include/, libtcs-xtce.so and libtcs-xtce.a with tcs-xtce.pc (and tcsccsds.pc, for the header-only time codes) in lib/, and the Python packages tcs_xtce and tcsccsds in lib/python3/site-packages/.

Packages. make deb and make rpm (or make packages, both) build two packages, version <version>-1, into build/packages/, since a package with operational code holds nothing else: tcsxtce, the operational code – the tcsxtce-* headers, the tcsxtce Python package and tcsccsds’s time codes, with tcsxtce.pc and tcsccsds.pc – and tcs-xtce, the software tools – the commands, libtcs-xtce with its headers and tcs-xtce.pc, the tcs_xtce Python package – with the documents and examples. tcs-xtce requires the tcsxtce built with it, and python3 3.10 or later. The packages also put /opt/tcs/bin on PATH and /opt/tcs/lib/pkgconfig on PKG_CONFIG_PATH for login shells, tell the loader about /opt/tcs/lib, and put the Python packages on python3’s path.

Installing and packaging use tcs-helpers, the packaging scripts and make rules the TCS projects share, from a checkout of it beside this one, so clone it there first (make test’s checks use it too). It is used where it is, never installed; TCS_HELPERS=<path> names a checkout elsewhere, and make tcs-helpers checks that it is there and new enough, 0.11.0 or later, which installing and packaging do first.

git clone https://github.com/vomlehn/tcs-helpers.git ../tcs-helpers
make install              # build the packages, install this system's
make install DRY_RUN=1    # show what install would do; change nothing
make uninstall            # remove the package
make uninstall DRY_RUN=1  # show what uninstall would do

make install builds both packages as you, and then installs the one this system takes with its usual installer: the .deb with apt-get on Debian and Ubuntu, the RPM with dnf (or yum) on Fedora and Red Hat’s, or with zypper on SUSE’s, each of which installs what the package depends on too. Only that step runs as root, under sudo, which asks for your password then; SUDO=<command> names another, and none is used when make runs as root. make uninstall removes the package with the same installer. DRY_RUN=1 has the installer show what it would do – apt-get -s, dnf --assumeno, zypper --dry-run – without sudo, changing nothing.

The system is known by the ID and ID_LIKE of /etc/os-release, not by which tools it has. On one it does not know, make install says so and stops; there, or to install the other kind, PACKAGE_FORMAT=deb or PACKAGE_FORMAT=rpm chooses the kind, and INSTALLER=<command> the installer (apt-get, apt, dpkg, dnf, yum, zypper or rpm). If the kind it needs was not built, because dpkg-deb or rpmbuild is missing, it says which to install; make deb and make rpm themselves say so and carry on without the tool, so that make packages builds what it can.

/etc/profile.d is read only by login shells, so sudo, cron and other minimal environments do not see /opt/tcs/bin. To make tcs-xtce, xtce-digest and tcs-xtcee available everywhere, link them into /usr/local/bin:

sudo /opt/tcs/sbin/tcs-xtce-links             # make the links
sudo /opt/tcs/sbin/tcs-xtce-links --remove    # take them away again

--dir DIR links into another directory, such as /opt/bin. Only the package’s own programs are linked, and anything already there that is not one of its links is left alone and named. Removing the package removes the links from /usr/local/bin and /opt/bin; installing it never makes them. After make install, sudo make links and sudo make unlinks do the same (LINKDIR gives the directory).

From the source tree. Build as yourself first, make && make editor, since root’s PATH seldom has cargo and a build as root would leave root’s files in the tree; then sudo make install-files copies the same files into place without a package, taking the editor as built, for development, which is what make install once did, but nothing outside /opt/tcs; make install-files PREFIX=$HOME installs under your home instead, DESTDIR stages it, and make uninstall-files, with the same variables, removes them. make install takes neither variable, and stops if given one. make stage copies into build/stage/<package>/, from which the packages are made.

make install-files, make stage and so the packages strip the libraries they install: libtcs-xtce.so of all a debugger needs (strip --strip-unneeded), libtcs-xtce.a of its debugging information (strip --strip-debug). Give STRIP=0, as in make packages STRIP=0, to keep everything as built.

The .deb also carries what Debian expects of every package, outside /opt/tcs as the hooks are: /usr/share/doc/tcs-xtce/copyright, in Debian’s machine-readable format, and changelog.Debian.gz, both made as the package is built from LICENSE-MIT and the version; lintian’s overrides in /usr/share/lintian/overrides/tcs-xtce; and a trigger that has dpkg run ldconfig once the library is installed or removed. The RPM says the same in its own License, %changelog, %post and %postun. make lint-packages checks the packages that make packages built with lintian and rpmlint, and their shell scripts with shellcheck. It skips, in a line, any of the three that is not installed, and fails on any finding that is not overridden; each override says why it is intended, in packaging/deb/tcs-xtce/lintian-overrides and packaging/rpm/rpmlint.toml.

Python. Three distributions, all libraries, which install no commands: tcs-xtce, the XML binding and the compiler, run as python3 -m tcs_xtce; tcsxtce, the packet runtime it depends on; and tcsccsds. make python-dist builds each as a wheel and an sdist in dist/, checks them with twine and tries them, and make python-versions tries them on each Python from 3.10 to 3.14, in containers. pip install --find-links dist dist/tcs_xtce-*.whl installs the compiler and the runtime; pip install ./python and pip install ., in that order, install them from the repository. None is on PyPI yet.

Rust. cargo add tcs-xtce (and cargo add tcsccsds); the crates come from crates.io and nothing here installs them.

C and C++. With /opt/tcs/lib/pkgconfig on PKG_CONFIG_PATH:

cc  prog.c   $(pkg-config --cflags --libs tcs-xtce)
c++ prog.cpp $(pkg-config --cflags --libs tcs-xtce)
cc  prog.c   $(pkg-config --cflags --libs --static tcs-xtce)   # libtcs-xtce.a

The shared library’s soname is libtcs-xtce.so.N, where N is the ABI version in cpp/abi-version, which changes only when a change breaks programs already linked against it; it is not the package’s version.

How it works

  1. Parse. python/tcs_xtce/binding/xsd.py reads SpaceSystem.xsd into a language-neutral model and flattens type inheritance (complexContent extensions). XSD constructs it does not support raise an error, so schema changes cannot silently produce incomplete bindings.
  2. Bind. binding.py maps every complex type to a record with attribute, text, element and <choice> fields. It checks that one element of lookahead is enough to decode each content model, boxes fields that would otherwise make recursive types infinitely large, orders types by dependency, and picks a finite default for every required choice.
  3. Emit. emit_rust.py, emit_cpp.py and emit_python.py generate the types and their readers and writers. Generated Rust is run through rustfmt.
  4. Sample. sample.py generates documents that use every element of every type reachable from <SpaceSystem>, and every alternative of every choice (see tests/samples/COVERAGE.txt).

The tests check that:

  • every sample validates against the official XSD (xmllint);
  • each library round-trips every sample (deserialize, serialize, deserialize, then compare);
  • the Rust, C++ and Python outputs are byte-identical; and
  • the serialized output also validates against the XSD.

Type mapping

XSD Rust C++ Python
complex type struct struct @dataclass
<choice> enum struct + std::variant @dataclass (name, value)
enumeration enum enum class str Enum
optional element or attribute Option<T> std::optional<T> Optional[T]
repeated element Vec<T> std::vector<T> list[T]
recursive field Box<T> xtce::Box<T> (plain reference)
string, dates, durations, hexBinary, unions String std::string str
boolean / long, integer / int / unsignedShort / double bool / i64 / i32 / u16 / f64 bool / int64_t / int32_t / uint16_t / double bool / int / float

Type names match the schema (SpaceSystemType, IntegerParameterType, …), and field names are the snake_case form of the XML names.

Managed buffers

Each library has a buffer type (tcs_xtce::Buffer in Rust, xtce::Buffer in C++, tcs_xtce.ManagedBuffer in Python) that is preallocated (64 KiB by default) and keeps its allocation between uses. A Document owns one input buffer and one output buffer alongside the root SpaceSystemType:

  • load and read_from copy the input into the input buffer and parse it in place; the Rust and C++ readers work on slices of that buffer and only copy data into the fields they fill;
  • serialize writes into the output buffer and returns a borrowed view of it, without allocating a new buffer;
  • both buffers are released when the Document is dropped, destroyed or garbage-collected (Python also has close() and with).

Usage

Rust:

use tcs_xtce::{Document, SpaceSystemType};

let mut doc = Document::from_bytes(&std::fs::read("sat.xtce")?)?;
println!("{}", doc.root.name);
doc.root.short_description = Some("updated".into());
let bytes: &[u8] = doc.serialize()?;      // view into the managed buffer

C++:

#include "tcs-xtce-document.hpp"

xtce::Document doc = xtce::Document::from_bytes(bytes);
doc.root.short_description = "updated";
std::string_view out = doc.serialize();   // view into the managed buffer

C:

#include "tcs-xtce.h"

xtce_document* doc = xtce_document_new(0, 0);
if (xtce_document_load(doc, data, len) != XTCE_OK)
        fprintf(stderr, "line %zu: %s\n", xtce_document_error_line(doc),
                xtce_document_error(doc));
const uint8_t* out; size_t n;
xtce_document_serialize(doc, &out, &n);
xtce_document_free(doc);

Python:

import tcs_xtce

doc = tcs_xtce.Document.from_file("sat.xtce")
doc.root.short_description = "updated"
with doc.serialize() as view:             # memoryview of the managed buffer
    sys.stdout.buffer.write(view)

Packet codecs

cd python
python3 -m tcs_xtce mission.xtce mission.rs --lang rust
python3 -m tcs_xtce mission.xtce mission.h  --lang c        # or --lang c++: same file
python3 -m tcs_xtce mission.xtce mission.py --lang python

Or install the Python distributions, compiler and runtime (see Installing), and run the compiler as a module from anywhere. They are not on PyPI yet:

make python-dist
pip install --find-links dist dist/tcs_xtce-*.whl
python3 -m tcs_xtce mission.xtce mission.rs --lang rust

--lang c and --lang c++ write the same header, which compiles both as C11 and as C++. It is self-contained (it includes only tcsxtce-packet.h), allocates nothing, and reports errors as return codes.

For each concrete SequenceContainer and MetaCommand, this generates a struct with decode and encode functions. Each inheritance tree also gets a <Root>Kind type that decodes a packet into whichever container or command it matches. Values fixed by restriction criteria or argument assignments (such as an APID or opcode) are written automatically and are not fields. Packets are encoded into managed buffers. A Codec owns an input buffer and an output buffer, preallocated to the largest packet size.

let mut codec = Codec::for_packet::<demo::CCSDSPacketKind>();
codec.load(&frame);
if let demo::CCSDSPacketKind::Housekeeping(hk) = codec.decode::<demo::CCSDSPacketKind>()? {
    println!("{} degC", hk.temperature);
}
let wire = codec.encode(&demo::SetMode { mode: demo::ModeArgType::SCIENCE, ..Default::default() })?;

Supported features:

  • every XTCE data type: integers (any size, every signed encoding and BCD; past 64 bits they are held with the bnum crate in Rust and with tcsxtce-bnum.h, a C and C++ library that mirrors it), floats (IEEE 754 16 to 128 bits, MIL-STD-1750A, DEC, IBM, TI), strings in every character set, binary, enumerations, booleans, times, arrays and aggregates, in any bit and byte order, with valid ranges checked when encoding;
  • polynomial, spline, math operation and context calibrators, also in aggregate members;
  • container inheritance with comparisons and boolean expressions, included and repeated containers, locations from either end and from the next entry, include conditions, container sizes, parameter segments (repeated too), indirect entries, messages, and transform algorithms the application supplies;
  • packet length fields, also of included containers, sizes and counts from other values, and error detection: CRCs, checksums, XOR and parity;
  • commands, including containers from a CommandContainerSet and other meta-commands’ containers, even whole commands;
  • missions split across several documents, with one digest for the set;
  • alarms, including the ones that depend on earlier samples, and MathAlgorithms;
  • fixed and variable frame streams, with frame synchronization, every PCM code including bi-phase, and custom streams that chain into them;
  • custom algorithms, which the application supplies as functions.

tcsccsds, in ccsds/, is a separate library of CCSDS standards that XTCE doesn’t define, in the same four languages: so far the CUC, CDS, CCS and ASCII time codes, and TAI and UTC with their leap seconds. See its README.

Warning: tcsccsds is an alpha release. It is not fully tested, it is not feature complete, and it is subject to rapid change. Until 1.0, any change to its API changes the minor version number (0.1 to 0.2), so a release that changes only the patch number never breaks code built against it. Feedback is welcome, even at this stage: open an issue at https://github.com/vomlehn/tcs-xtce/issues.

See the manual for the exact list. tests/packet_check.sh checks that Rust, C, C++ and Python produce identical results on hand-built and random packets.

Behaviour and limitations

  • The bindings follow XTCE 1.3 strictly. Documents written for older versions are rejected wherever the schema changed. For example, 1.3 no longer allows the rangeAppliesToCalibrated attribute, and FixedValueEntry now requires sizeInBits. Errors give the line number.
  • Elements are matched by local name; the namespace URI is not checked.
  • Values that the schema constrains only by patterns, ranges or xs:key are stored but not validated. Use xmllint with references/catalog.xml for full validation.
  • Schema default values are not filled in: an attribute that was not present stays None / empty, so documents round-trip as written. The defaults appear in the generated documentation comments.
  • Comments, processing instructions and attributes in other namespaces (such as xsi:schemaLocation) are not preserved. Doubles are written in their shortest round-trip form.
  • xs:integer is stored as a 64-bit integer.

Incompatible changes

tcsccsds 0.3.0: tcs-ccsds is renamed tcsccsds. Its time codes run aboard and in the operations center, so it takes an operational name, as tcsxtce did: the crate tcs-ccsds is now tcsccsds, the Python package tcs_ccsds is tcsccsds (Python package version 0.3.0, the crate’s), the header ccsds-time.h is tcsccsds-time.h, and tcs-ccsds.pc is tcsccsds.pc. The functions, types and macros keep their names, ccsds_ in C.

0.7.0: the packet runtime is a library of its own, tcsxtce. What code that tcs-xtce generated runs on – the packet runtime – is operational code, while the rest of tcs-xtce is software tools, and the two are now named apart: a name that starts tcs and a letter is operational code, one that starts tcs- or tcs_ is not. Code that tcs-xtce generated has to be generated again, and depends on the runtime rather than on tcs-xtce.

The header-only C/C++ runtime has a pkg-config file of its own, tcsxtce.pc, which needs no library. The functions, types and macros keep their names.

0.6.0: OMG’s documentation is no longer copied. The generated code describes each XTCE declaration in a line of its own, where it used to carry the schema’s documentation, which is OMG’s and may not be redistributed; versions 0.1.0 to 0.5.0 were withdrawn from crates.io for that reason. Nothing the generated code does, and no name in it, changed, so code using it needs no change.

0.5.0: wide enumerations hold wide integers. An enumeration whose integer encoding has more than 64 bits now holds its value in the type a wide integer of that encoding has, rather than a 64-bit one, so that raw values no label lists survive decoding and re-encoding: in Rust a u128, an i128 or a bnum integer instead of i64, and in C and C++ the xtce-bnum.h integer instead of int64_t, with label macros that are XTCE_BN_LIT constants. Code using such an enumeration’s value changes with it; code that tcs-xtce generated has to be generated again. The Rust runtime’s wide_to_i64, which only that code used, is gone. Enumerations on encodings of 64 bits or fewer are unchanged.

0.4.0: the C and C++ headers were renamed. They are no longer in the directories xtce/ and ccsds/ but straight in the include directory, each with its library’s prefix, so that installed in a shared include/ none is mistaken for another library’s, and ccsds-time.h cannot shadow the system’s <time.h>. Change each #include as below; code that tcs-xtce generated has to be generated again.
